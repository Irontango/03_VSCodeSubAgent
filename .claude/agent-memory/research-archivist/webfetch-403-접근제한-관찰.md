2026-08-03 라즈베리파이 OpenCV 차선 인식 리서치([[라즈베리파이-opencv-차선인식-리서치-2026-08-03]]) 중 관찰된 현상:

**관찰 내용:** WebFetch 도구가 arxiv.org, nature.com, researchgate.net, dl.acm.org, pmc.ncbi.nlm.nih.gov, mdpi.com, web.archive.org, tumblr.com, circuitdigest.com, zbotic.in, hackster.io, docs.donkeycar.com 등 다수의 학술/블로그 도메인에서 반복적으로 HTTP 403(접근 거부)을 반환함. 이 때문에 원문 직접 대조가 불가능해 WebSearch가 제공하는 스니펫/캐시 정보에 크게 의존해야 했음(예: CircuitDigest 발행일 추정 시 Wayback Machine 직접 대조를 시도했으나 403으로 실패, Tumblr 재게시 URL 패턴이라는 간접 근거로 대체함).

**주의:** 현재까지는 **단일 세션(2026-08-03) 관찰**이며, 이전 리서치 세션([[rc카-자율주행-리서치-2026-07-19]], [[초음파-센서-장애물회피-리서치-2026-07-20]])에서는 이런 현상이 기록되지 않았음. 세션/환경 특성(예: 프록시, 일시적 차단, 네트워크 설정)일 가능성이 있으므로 아직 일반화하지 말 것.

**Why:** WebFetch 접근 실패가 반복되면 source-verifier의 원문 직접 대조 검증이 구조적으로 어려워지고, WebSearch 간접 확인에만 의존하게 되어 검증 신뢰도가 낮아질 위험이 있음.
**How to apply:** 
- 향후 리서치에서도 동일한 도메인 군에서 WebFetch 403이 재현되는지 계속 관찰하고, 재현될 경우 이 메모에 "재확인" 기록을 추가할 것 (기존 [[리서치-발행일-검증-방법론]], [[arxiv-논문공장-탐지-방법론]] 사례처럼 세션 간 재확인 누적 방식을 따름).
- 재현이 확인되면 source-verifier에게 "원문 접근 불가 시 WebSearch 스니펫 기반 판단임을 명시적으로 표기"하도록 안내하는 것을 표준 절차로 승격 고려.
- 2회 이상 세션에서 재현되지 않으면 이 메모는 세션 특이적 노이즈로 간주하고 우선순위를 낮출 것.

**재확인 (2026-09-28, 에러 유형 변화 + 도메인 유동성 신규 확인):** 라즈베리파이 OpenCV 차선 인식 4회차 격주 후속 리서치([[라즈베리파이-opencv-차선인식-리서치-2026-09-28]])에서 접근 차단 현상 자체는 재현됨(arxiv.org, fleetstack.io) — 다만 에러 유형이 HTTP 403이 아니라 **EGRESS_BLOCKED**로 나타남. 결과적으로 원문 직접 대조가 불가능하다는 실질적 영향은 동일. **신규 발견**: 이번 회차엔 github.com이 정상 동작(403 미재현)한 반면, 지난 회차엔 문제없던 api.github.com(GitHub API)이 신규로 403 차단됨 — **차단 패턴이 도메인별·세션별로 유동적**이며 "GitHub 전체가 차단/허용"처럼 일괄 판단할 수 없음이 확인됨. 대응으로 GitHub API 대신 웹페이지 직접 렌더링으로 우회함. 이 관찰은 이제 3개 세션(2026-08-03, 2026-09-28; 그 사이 회차 기록은 없으나 현상 자체는 재발)에 걸쳐 반복되므로 "세션 특이적 노이즈"가 아니라 **환경의 구조적 특성(프록시/egress 정책이 도메인·시점별로 다르게 적용됨)**으로 격상해 취급할 것을 권고.

**재확인 (2026-10-12, api.github.com 403 재발 + DNS 실패 신규 유형):** RC카 PWM/GPIO 모터 제어 동향 격주 후속 1회차([[pwm-gpio-모터제어-리서치-2026-10-12]])에서 **api.github.com(GitHub REST API)이 다시 403으로 전면 차단됨**(2026-09-28에 이어 재발) — GitHub HTML 페이지를 WebFetch로 직접 열람해 우회함. 이번 회차의 **신규 발견**은 **gpiozero.readthedocs.io가 DNS 해석 실패(ENOTFOUND)**로 접근 자체가 불가능했다는 점으로, 기존 403/EGRESS_BLOCKED와는 다른 **세 번째 실패 유형**임. 대응으로 GitHub raw changelog.rst(원문 1차 소스)로 대체 검증함. PyPI JSON API(pypi.org/pypi/.../json)는 이번에도 정상 작동 — PyPI는 지금까지 모든 세션에서 차단 사례가 보고되지 않아 **릴리스/버전 확인용 1차 소스로 상대적으로 신뢰할 수 있는 채널**로 재확인됨. 4개 세션(2026-08-03, 2026-09-28, 2026-10-12; 2026-08-17/08-31/09-14 회차는 명시적 기록 없음)에 걸쳐 차단 현상이 지속·변주되므로, "환경의 구조적 특성"이라는 기존 격상 판단이 재확인됨. 매 회차 초반에 주요 도메인(api.github.com, 대상 docs 사이트 등) 접근성을 먼저 점검하고 실패 시 즉시 대체 경로(HTML 직접 열람, raw 파일, PyPI API 등)로 전환하는 것을 표준 절차로 권고.

**재확인 (2026-10-26, DNS 실패 유형이 다른 도메인 군에서 재현):** Flutter+라즈베리파이 WebSocket 원격 제어 격주 후속 2회차([[flutter-웹소켓-라즈베리파이-원격제어-리서치-2026-10-26]])에서 `huggingface.co`, `flutter.dev` 계열, `wiki.seeedstudio.com` 등에 대한 WebFetch 직접 접근이 **DNS 해석 실패(ENOTFOUND)**로 막힘 — 2026-10-12에 `gpiozero.readthedocs.io`에서 처음 관찰된 것과 **동일한 실패 유형(DNS)이 전혀 다른 도메인 군에서 재현**된 것으로, 403/EGRESS_BLOCKED와는 뚜렷이 구분되는 세 번째 유형(DNS ENOTFOUND)이 "1회성 이상 현상"이 아니라 **재발 가능한 패턴**임이 확정됨. 대응으로 WebSearch 스니펫 기반 교차검증으로 대체함(원문 1차 도메인 직접 열람 대신). 5개 세션(2026-08-03, 2026-09-28, 2026-10-12, 2026-10-26)에 걸쳐 차단/실패 현상이 지속·변주되므로, 매 회차 시작 시 "이번 세션에 어떤 도메인이 어떤 유형(403/EGRESS_BLOCKED/DNS)으로 막히는지" 선제 점검하는 절차를 모든 서브에이전트(특히 web-researcher, source-verifier)의 표준 작업 순서에 포함할 것을 권고.

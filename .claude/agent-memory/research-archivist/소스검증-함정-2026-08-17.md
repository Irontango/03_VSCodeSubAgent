RC카 PWM/GPIO 모터 제어 리서치([[pwm-gpio-모터제어-리서치-2026-08-17]]) 중 source-verifier가 발견한 품질관리 함정 3건:

1. **연도 오기(2024→2026) 정정 사례.** web-researcher가 Adafruit_CircuitPython_PCA9685 최신 릴리스(3.4.22)를 "2024-04-23"이라고 보고했으나, source-verifier가 GitHub Releases API·Tags API·PyPI 3곳을 교차 확인한 결과 실제로는 **2026-04-23**이었음(연도만 틀림). 이 오류로 인해 "PCA9685 릴리스가 2024년에 정체됐다"는 잘못된 결론이 도출될 뻔했으나 정정하여 "정체 없이 최근까지 활발히 유지보수"로 최종 보고서에 반영함. [[리서치-발행일-검증-방법론]]과 같은 계열의 함정(발행일 오인)이지만, 이번엔 "오래된 콘텐츠를 최신으로 오인"이 아니라 "연도 숫자 자체를 착오"한 변종 사례.

2. **GitHub API license 필드 오분류.** RpiMotorLib(gavinlyonsrepo) 저장소의 GitHub API `license` 필드는 "Other"로 표시되지만, LICENSE 파일 원문을 직접 대조하면 실제로는 GPLv3임을 확인함. GitHub API의 자동 라이선스 감지가 실제 라이선스 텍스트와 다르게 분류될 수 있으므로, 라이선스 확인 시 API 필드만 믿지 말고 LICENSE 파일 원문을 직접 대조할 것.

3. **WebFetch의 JS 기반 GitHub 릴리스 페이지 오독.** WebFetch가 JavaScript 렌더링 기반 GitHub 릴리스 페이지를 "릴리스 없음"으로 잘못 요약한 사례가 있었음. 가능하면 GitHub REST API(releases/tags 엔드포인트) 또는 PyPI API 기반으로 1차 확인하는 것을 우선할 것 — WebFetch로 GitHub 웹 UI를 직접 스크레이핑하는 방식은 신뢰도가 낮음.

**Why:** 위 3건 모두 source-verifier 단계에서 다중 소스 교차확인을 통해 걸러졌으나, 만약 단일 소스만 사용했다면 최종 보고서에 오류가 그대로 반영될 뻔했음. 이런 함정들이 반복될 가능성이 높으므로 사전에 알려두는 것이 효율적.
**How to apply:** (a) web-researcher가 보고하는 날짜/연도는 특히 "20xx년"류 표기를 재확인 대상으로 항상 의심할 것(연도 오기 패턴). (b) 라이선스 확인은 GitHub API 필드 대신 LICENSE 파일 원문 대조를 표준 절차로 삼을 것. (c) GitHub 릴리스/커밋 이력 확인은 WebFetch보다 GitHub API·PyPI API를 우선 사용할 것.

**재확인 (2026-10-12, PWM/GPIO 모터제어 격주 후속 1회차): 검증 함정 2건 추가.** RC카 PWM/GPIO 모터 제어 동향 격주 후속 리서치([[pwm-gpio-모터제어-리서치-2026-10-12]])에서 신규로 확인된 패턴:

4. **"검색 결과 부재 ≠ 실재 부재" — WebSearch 음성 결과를 과신하지 말 것.** 1회차(2026-08-17)에서 web-researcher가 "찾지 못함(미확인 공백)"으로 결론지었던 **pigpio-rp5(kshetline)**와 **nick-hunter의 TB6612FNG 프로젝트** 두 건 모두, 이번 회차에 **GitHub 프로필을 WebFetch로 직접 열람**하자 즉시 실존이 확인됨(각각 Unlicense/0★, 10★·6forks). 두 사례 모두 GitHub 사용자명/레포명 후보가 이미 특정되어 있었음에도 WebSearch 색인 누락으로 "없음"처럼 보였던 것. [[flutter-웹소켓-라즈베리파이-원격제어-리서치-2026-08-31]]에서 확인된 "description 공란 저장소 검색 누락" 패턴과 같은 계열이며, 이번 회차로 "특정 GitHub 계정/레포명 후보가 있으면 WebSearch 결과가 음성이어도 반드시 프로필 직접 열람으로 재확인한다"가 **표준 절차로 격상**됨.

5. **애그리게이터(3rd-party 캐시) 수치 자체가 stale할 수 있음 — 날짜뿐 아니라 스타 수 등 모든 지표가 대상.** 이번 회차에 두 건에서 동시에 재확인됨: (a) RpiMotorLib — gittrend.io(2026-03-29 표기)와 ecosyste.ms(2024-03-28 표기)가 서로도 불일치하고 GitHub 1차 소스(2026-05-11)와도 불일치. (b) pid_py(ThunderTecke) — 기존 참고자료 캐시 수치 "2023-08 / 4★"가 실제로는 "2024-05-27 / 13★"로 과소평가되어 있었음. 기존 "최근 업데이트일만으로 활성 판단 금지"(2026-09-28, [[리서치-발행일-검증-방법론]]) 교훈을 한 단계 더 확장하여 — **"집계 사이트(gittrend.io, ecosyste.ms 등)가 제공하는 날짜·스타 수 등 모든 수치는 그 자체로 stale할 수 있으므로, GitHub 1차 소스로 재확인하기 전에는 인용하지 않는다"**는 원칙을 표준 절차로 추가함.

**How to apply (2026-10-12 추가):** (d) web-researcher/source-verifier는 특정 GitHub 사용자명·레포명이 거론되었는데 WebSearch로 검출되지 않을 경우, 결론을 내리기 전에 반드시 `github.com/<user>/<repo>` 프로필 페이지를 WebFetch로 직접 열람할 것. (e) 애그리게이터 사이트(gittrend.io, ecosyste.ms 등)에서 얻은 날짜/스타 수 등 수치는 "참고용 1차 추정치"로만 취급하고, 최종 보고서에 반영하기 전 GitHub 저장소 페이지에서 반드시 재대조할 것.
